## Project status

Working. `python main.py` runs all five visualizer paths end-to-end with no unhandled exceptions, and the test suite passes (`pytest tests/ -v`). A prior version of this project had several correctness bugs (silently-wrong saliency, a crashing seq2seq path, a broken attention-head plot); see `ASSESSMENT.md` for the original diagnosis — those findings are now resolved, and `ASSESSMENT.md` is left in place as a point-in-time record, not current status. `EXTENSION_PLAN.md` tracks what's built vs. explicitly deferred for future architectures/techniques (vision support, linear probing, cross-model comparison, a Streamlit UI).

## What this is

A small wrapper library around Hugging Face `transformers` for visualizing how transformer models make predictions, via saliency maps (input-gradient based) and attention heatmaps. It targets five model families: text classification, token classification, extractive question answering, causal-LM generation, and seq2seq — plus a handful of opt-in deeper interpretability techniques (Integrated Gradients, logit lens, attention rollout, attention entropy/distance) layered on top of the same per-layer attention/hidden-state capture.

## Setup & running

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt   # runtime deps + pytest
.venv/bin/python main.py
.venv/bin/pytest tests/ -v
```

`main.py` is the example entry point. It runs all five visualizers end-to-end against small public checkpoints (`hf-internal-testing/tiny-random-bert` for classification/token-classification/QA, `distilgpt2`, `Helsinki-NLP/opus-mt-en-fr`) and writes PNGs to `visualizations/<classification|token_classification|question_answering|generative|seq2seq>/`, plus a demo call to each opt-in technique (Integrated Gradients, logit lens, attention rollout, attention entropy/distance). Checkpoints are downloaded from the Hugging Face Hub on first run and cached locally — expect network access on first run. Each demo block in `main.py` is wrapped in its own `try/except` so one model's failure doesn't hide the others.

`tests/test_visualizers.py` uses smaller/random-weight checkpoints (`hf-internal-testing/tiny-random-bert`, `sshleifer/tiny-gpt2`, `patrickvonplaten/t5-tiny-random`) for speed. One exception: the equivalence test uses `Helsinki-NLP/opus-mt-en-fr`, because T5 does not scale its embeddings and the tiny random Marian checkpoint does not load under v5. The logit-lens test uses `distilgpt2`, because `tiny-gpt2` has a hidden size of 2. A LayerNorm over 2 values always gives ±1, so that model cannot detect a double-applied norm. `pytest.ini` sets `pythonpath = .` since the package isn't installed/packaged — pytest needs that to import `model_understanding` from the repo root.

**Checkpoint choice matters here.** `AutoTokenizer`/`AutoModel*` under `transformers` v5 require a repo to ship a modern `tokenizer.json` (fast tokenizer) and a `model_type` key in `config.json`; older community checkpoints from ~2020–2021 (e.g. the original `prajjwal1/bert-tiny`) may have neither and will fail to load with a fairly opaque `ValueError`. If you swap in a different example/test checkpoint, sanity-check it loads under the currently pinned `transformers` before wiring it in.

## Architecture

Everything lives in `model_understanding/transformers_wrapper.py`; `model_understanding/__init__.py` just re-exports it (`from .transformers_wrapper import *`).

- **`BaseVisualizer`** (ABC) — shared machinery all visualizers build on:
  - Loads an `AutoTokenizer` + model (subclass-supplied via `_load_model`), moves it to `cuda` if available else `cpu`.
  - **Every subclass's `_load_model` passes `attn_implementation="eager"`.** This is required, not cosmetic: SDPA/flash attention implementations (the default on recent `transformers`) don't materialize attention probabilities, so `output_attentions=True` would silently return `None` for `outputs.attentions` without this. `attn_implementation` as a `from_pretrained` kwarg needs `transformers>=4.36.0`, which is why that's the pinned floor in `requirements.txt`.
  - `_input_embeddings(input_ids)` is the **single, shared** source of raw input embeddings for every subclass's `compute_saliency` — dispatches on `model.config.is_encoder_decoder` (encoder-side `get_encoder().get_input_embeddings()` for seq2seq, `get_input_embeddings()` otherwise, with an `embed_tokens` fallback for encoder submodules that don't implement `get_input_embeddings()`). This exists specifically so the "don't double-apply position encoding/LayerNorm" fix (see `ASSESSMENT.md` bug #1) can't independently regress in one subclass while staying fixed in the others — every new architecture should call this rather than reimplementing embedding lookup. It also multiplies by `embed_scale` when the module that owns the embeddings has one (Marian, Pegasus). Those models apply the scale only when they get `input_ids`. Models that scale inside the embedding module (BART, M2M100) have no such attribute.
  - `_non_id_inputs(inputs, batch_size=1)` returns every tokenizer output except `input_ids`. Pass it with every `inputs_embeds` call. If you pass only `attention_mask`, `token_type_ids` drop out, and sentence-pair inputs (QA) get a different output. `batch_size` expands the tensors for Captum, which runs all IG steps as one batch.
  - `_tokens(input_ids)` returns the token strings. It indexes `[0]`, because `squeeze()` returns a single string for a one-token input.
  - `test_saliency_forward_pass_matches_plain_forward_pass` is the guard for this whole class of bug. It hooks the real `compute_saliency` forward pass for every visualizer type and compares it with `model(**inputs)`. Add each new architecture to `SALIENCY_CASES`.
  - `self.attention_weights` / `self.layer_outputs` are populated by `_capture_layerwise(attentions, hidden_states)`, called from each subclass's `compute_attention` with the real `outputs.attentions`/`outputs.hidden_states` (or `outputs.encoder_attentions`/`outputs.encoder_hidden_states` for the seq2seq encoder-side view) from a forward pass run with `output_attentions=True, output_hidden_states=True`. There is no forward-hook machinery for *capturing* this data — it doesn't exist in this codebase, and if you're tempted to add hook-based capture for some new use case, don't: HF module names/return shapes vary by architecture and hooking them reliably is much harder than it looks (this was tried before and produced a class of bugs — see `ASSESSMENT.md` bug #4 for the specifics if you want the cautionary tale). Forward hooks *are* used for one different purpose — see activation patching below — but only to intervene on an already-known, verified module path (`self.model.base_model.h` / `.encoder.layer`), never to guess which module is "the attention one" by name-matching.
  - `_get_hidden_state_at(input_ids, layer_idx, position, **model_kwargs)` / `_patch_hidden_state_at(input_ids, layer_idx, position, value, **model_kwargs)` are the shared mechanics behind activation patching: a temporary `register_forward_hook` on `self._transformer_layers()[layer_idx]` (implemented per-subclass — `ClassificationVisualizer` → `self.model.base_model.encoder.layer`, `GenerativeVisualizer` → `self.model.base_model.h`; both confirmed to return a plain `torch.Tensor` from `forward()` in the pinned `transformers` version, not a tuple) that either reads or overwrites the hidden state at one `(layer, position)`, then removes itself. `compute_activation_patch_sweep(clean_text, corrupted_text)` calls `self.compute_activation_patch` (subclass-provided) across every `(layer, position)` pair and returns a `[num_layers, seq_len]` grid; `plot_activation_patch_sweep` renders it as a diverging heatmap. This is the one place the codebase intervenes mid-forward-pass rather than just reading `output_attentions=True`/`output_hidden_states=True` afterward — necessary because patching requires *changing* the computation, not just observing it. Cost note: each `compute_activation_patch` call does 4 forward passes (clean baseline, corrupted baseline, one read-hook pass, one patch-hook pass), so the sweep is `4 × num_layers × seq_len` forward passes — fine for the tiny demo checkpoints, but don't assume it scales to real models/long sequences without hoisting the two baseline passes out of the loop first. `BaseVisualizer._transformer_layers()` has a default that raises `NotImplementedError` (not `AttributeError`) for any subclass that doesn't override it, so calling activation patching on an unsupported visualizer fails with a clear message instead of an opaque internal error.
  - `compute_attention_rollout()` / `compute_attention_entropy_distance()` are generic, concrete on the base class, and work for **any** subclass once `self.attention_weights` is populated (call `compute_attention` first) — pure tensor post-processing, no new forward pass. Rollout composes per-layer head-averaged attention via `0.5·A + 0.5·I` (residual-stream correction) chained by matrix multiply across layers; entropy/distance are per-head scalars. Both are covered by exact synthetic-tensor tests (uniform → `log(seq_len)` entropy, one-hot → `0` entropy) rather than model-dependent ones.
  - `analyze(text, save_dir)` is the top-level orchestration method: `compute_saliency` → `compute_attention` → `plot_layer_attention` → `plot_attention_heads` → `plot_layer_activations` → `plot_gradient_flow`, saving each PNG into `save_dir` if given. `Integrated Gradients`, `logit lens`, `attention rollout`, and `attention entropy/distance` are **not** part of this default flow — they're opt-in methods called separately (see `main.py` for example usage) so `analyze()`'s runtime and tested contract stay stable. **None of the opt-in methods write to `self.attention_weights`/`self.layer_outputs`** — only `compute_attention` does. `compute_logit_lens` originally called `_capture_layerwise(None, outputs.hidden_states)`, which wiped `self.attention_weights` (since `attentions=None`) even though `compute_attention` had already populated it — silently breaking `compute_attention_rollout()`/`plot_layer_activations()` if called afterward on the same instance. If you add a new opt-in method that reads model internals, have it return its own results rather than touching this shared state.
  - `compute_faithfulness(attributions, *texts, fractions=(0.1, 0.2, 0.5))` is generic on the base class and opt-in. It scores a per-token attribution with comprehensiveness (`p(full) - p(top-k removed)`, higher is better) and sufficiency (`p(full) - p(only top-k kept)`, lower is better), plus their AOPC means. Rules:
    - It removes a token by setting its input embedding to zero (the IG baseline). This keeps the sequence length, so it works for every visualizer. IG gets a built-in advantage on this metric.
    - It never ranks or removes special tokens. It gets them from `get_special_tokens_mask(..., already_has_special_tokens=True)`. Do not pass `return_special_tokens_mask=True`, because `_non_id_inputs` then sends that key to the model.
    - `k = ceil(fraction × content tokens)`, and at least 1 for a fraction above 0. Python's `round` gives `k = 0` for small inputs, and comprehensiveness then reads 0 with no warning.
    - Each subclass implements `_target_probability(inputs, embeddings, target=None)` with the same target as its `compute_saliency`: the predicted class, the next token, the first decoder token, the mean of per-token label probabilities (token classification), or `p(start) × p(end)` (QA). A new visualizer must implement it too.
    - `test_faithfulness_removes_the_top_ranked_content_token` checks the ranking and the mask positions. It fails for a reversed sort or a missing special-token offset. The bookkeeping identities (comprehensiveness at 0 is 0, and so on) cannot catch those bugs.
    - Use a trained model for real scores. The tiny random checkpoints give near-uniform probabilities, so their scores are noise. `main.py` runs the demo on `distilgpt2` and compares saliency and IG with a random ranking.
  - Plotting methods (`plot_saliency`, `plot_attention`, `plot_layer_attention`, `plot_attention_heads`, `plot_layer_activations`, `plot_gradient_flow`, `plot_logit_lens`, `plot_attention_entropy_distance`, `plot_faithfulness`) are concrete on the base class and shared by all subclasses. Integrated Gradients and attention rollout don't get dedicated plot methods — they reuse `plot_saliency`/`plot_attention` directly, since their output shapes (one score per token; a token-by-token matrix) already match.

- **Subclasses** implement the three abstract methods (`_load_model`, `compute_saliency`, `compute_attention`), each following the same pattern: `self._reset_gradients()` (zeroes `model.grad` so repeated `analyze()` calls on the same instance don't accumulate gradients) → tokenize → `self._input_embeddings(input_ids)` → forward pass with `inputs_embeds` → backprop from the relevant logit → normalize `|gradient|` into a saliency map; and separately, a `torch.no_grad()` forward pass with `output_attentions=True` for the attention heatmap.
  - `ClassificationVisualizer` — `AutoModelForSequenceClassification`; saliency/attention driven by the argmax predicted class logit. Also has `compute_integrated_gradients(text, n_steps=50)` (Captum, zero-embedding baseline, same target logit; returns `(tokens, attributions, convergence_delta)` — `delta` is the completeness-axiom check, tested to be near-zero) and `compute_activation_patch(clean_text, corrupted_text, layer, position)` (see below).
  - `TokenClassificationVisualizer` — `AutoModelForTokenClassification`; saliency target is the sum of every token's own predicted-label logit (one backward pass, one saliency score per token — not per-label).
  - `QuestionAnsweringVisualizer` — `AutoModelForQuestionAnswering`; **the one class whose signature deliberately diverges** — `compute_saliency`, `compute_attention`, and `analyze` all take `(question, context, ...)` instead of a single `text` string, since that's what extractive QA actually needs. `analyze`'s body is a duplicate of `BaseVisualizer.analyze` for this reason (the only such duplication in the codebase) rather than a forced single-string abstraction. Saliency target: predicted answer span's `start_logit + end_logit`, backpropagated jointly.
  - `GenerativeVisualizer` — `AutoModelForCausalLM`; saliency driven by the next-token logit at the final position. Also has `compute_integrated_gradients` (next-token logit target), `compute_logit_lens(prompt)` — projects each captured hidden-state layer through the model's final norm (`self.model.base_model.ln_f`, GPT-2-style only; skipped gracefully, not faked, if absent) + `get_output_embeddings()`, returning top-1 `(token, probability)` per layer (the **final** layer's result is an exact reconstruction of the model's real next-token prediction, not an approximation — that exactness is what the regression test checks. GPT-2's last `hidden_states` entry already has `ln_f` applied, so the method applies `ln_f` only to the earlier layers. A previous version applied it two times to the last layer, and the `tiny-gpt2` test could not detect it) — and `compute_activation_patch(clean_text, corrupted_text, layer, position)`.
  - **`compute_activation_patch`** (`ClassificationVisualizer`/`GenerativeVisualizer` only): "noising" direction — caches the *corrupted* run's hidden state at `(layer, position)` via `_get_hidden_state_at`, splices it into the *clean* run at the same `(layer, position)` via `_patch_hidden_state_at`, and reports `patch_effect = (clean_prob - patched_prob) / (clean_prob - corrupted_prob)` for the clean run's predicted class/next-token (0 = patching had no effect, 1 = patching fully reproduced the corrupted prediction). Raises `ValueError` if `clean_text`/`corrupted_text` don't tokenize to the same number of tokens — position-based patching is only meaningful when positions line up 1:1. **Patching a run with its own hidden state must leave the output exactly unchanged** (`torch.equal`, not `allclose`) — this is the regression test, and it's what actually proves the hook only touches the intended slice. `main.py`'s generative demo (`distilgpt2`) documents honestly that its patch-effect numbers are noisy, not wrong — `distilgpt2` is too small/undertrained to confidently do the factual-recall task in the demo prompt, a known limitation of tracing experiments on small models, not a bug in the mechanism (which the exact-equality test already verifies independently of any model's actual competence).
  - `Seq2SeqVisualizer` — `AutoModelForSeq2SeqLM`; saliency/attention driven by the first decoder step, seeded via `_decoder_start_ids()` (a single `decoder_input_ids` token from `config.decoder_start_token_id`, falling back to `pad_token_id`). This is required — encoder-decoder models raise if neither `decoder_input_ids` nor `labels` is supplied. Attention/hidden-state capture uses `outputs.encoder_attentions`/`outputs.encoder_hidden_states` (encoder self-attention over the input), not decoder/cross-attention.

When adding a new model family, subclass `BaseVisualizer`, implement the three abstract methods using `self._input_embeddings()` for the embedding source, and reuse the existing plotting methods rather than duplicating the plotting infrastructure. `EXTENSION_PLAN.md` has the deferred list (vision, linear probing, cross-model comparison, Streamlit UI) if you're picking up the next slice of work.
